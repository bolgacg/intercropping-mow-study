This page runs the mow decision rule from your crop service, unchanged, against fifteen years of past Danish weather in the Spring 2026 trial settings from your repository. It is written for the people who configure and supervise that trial. At the end you will know which of the rule's four settings decides the day the rover is sent to cut the clover, and there is a two-patch change that lets a trial set all four.

1 · What the rule gets right

Standing on 1 May 2026, the rule already knows roughly when to cut

A mow recommendation only helps a farmer if it arrives early enough to plan around and does not swing with weather nobody can know yet. This test uses the real 2026 weather up to 30 April; after that, each run borrows the rest of the year from one past year, 2015 to 2025, and one run uses the day-by-day average of those eleven.

Click any row to read its three cut dates in the box under the chart. The average-weather row is selected to start.

What you see. Twelve simulated 2026 seasons, one per row; each dot is a day the rule recommended a cut and the simulated farmer cut. How to read it. Rows differ only in the weather after 30 April. Dots that line up vertically mean the weather after 1 May barely changes that cut. The take-away.

So the rule answers the question of when. The next question is which of its settings that answer depends on, which needs the vocabulary below.

Primer

The rule opens four gates, and a trial can set one of them

  1. In strip intercropping, a cash crop (here spring wheat) grows in strips beside strips of a service crop (here a clover and lucerne mix) that stays in the field as a living mulch.
  2. The clover shades the wheat, so a rover mows the clover strips; the practical question is on which day.
  3. Your crop service simulates both crops day by day with LINTUL1Strip, a crop model built on how much light each strip intercepts, and a separate rule, apply_mow_decision, reads that simulation and marks each day as recommended, blocked or neither.
  4. The rule recommends a cut only on a day when all four gates below are open.
  5. Only one of the four, the competition threshold, can be set from the trial file, the API or the dashboard; the other three are constants in mow_decision.py.
GATE A · HEIGHT
clover ≥ 15 cm
MIN_MOW_HEIGHT_CM, a constant in source
GATE B · RECOVERY
≥ 28 days since last cut
MIN_MOW_INTERVAL_DAYS, a constant in source
GATE C · COMPETITION
index > threshold (0.25 in Spring 2026)
mowThreshold: trial file, API and dashboard
GATE D · WHEAT STAGE
wheat emerged, not flowering to ripening
a fixed set of stages in source

A fifth value, CRITICAL_COMP_INDEX (0.45, also a constant), does not open or close anything; above it a recommended day is labelled "critical" instead of "recommended".

competition index
The crop model's daily light-competition index for the clover strip, 0 to 1. Near 1 means the clover takes almost all the light, as it does while the wheat is not yet up.
first cut
The first day in a season the rule recommends mowing; the date this page measures.
day of year
1 January is day 1; day 140 is 20 May in a year that is not a leap year.
closed loop
The simulated farmer cuts on the first day of each recommendation window, the season is re-run with that cut, and so on until the rule recommends nothing new.
ERA5
The European weather reanalysis, past weather reconstructed from observations, served here by Open-Meteo through your own weather_provider.
Spring 2026 settings
From crop_model/trials/Spring 2026.json: wheat sown 1 May, clover regrowing from 1 March, threshold 0.25.
2 · Which setting moves the first cut

The threshold on the dashboard, against the height in the source file

A trial manager who wants the rover out earlier or later will reach for the setting the dashboard offers. This section checks whether that setting reaches the date, across fifteen completed years of weather, 2011 to 2025.

What these numbers are and are not

  • Model outputs, not field measurements. The comparison is between settings of a decision rule inside your own model and claims nothing about a real field.
  • The Python reference, not the paper-facing model. The runs use lintul1strip_sim.py, the in-process reference in your repository. The C# LINTUL1Strip model behind the other providers needs dotnet, which I could not run, so its crop physics may give other dates. The decision rule is the same code on both paths.
  • The accept policy is mine. The simulated farmer cuts on the first day of each recommendation window. A farmer who waits a few days gets later dates.
  • The clover's modelled height rests on placeholders. H0, Hmax and GRH in lintul1strip_sim.py are marked PLACEHOLDER in your source. The size of the shift the height produces depends on them. That the threshold row is flat does not: it is flat at every height tested.
  • One trial shape. Spring wheat sown 1 May with the clover regrowing from 1 March, as in the Spring 2026 file. Other sowing dates, crops and service crops were not swept here.

3 · Why the threshold does not decide here

The competition gate opens in March; the height gate opens in May

The order in which the four gates open tells you which one sets the date, and also when the threshold would start to matter. This is one uncut season, 2019 weather, Spring 2026 settings.

Competition threshold

Change the threshold: the dashed line moves, but the index is already near 1 on the day it crosses any of them, so the competition bar and the first recommended day stay put.

What you see. Top, the competition index each day with the threshold dashed; middle, the modelled clover height with the 15 cm gate dashed; bottom, when each gate is open. How to read it. The rule can recommend only where all bars overlap. The vertical line is the first such day. Gate B is open all spring because nothing has been cut yet. The take-away.

The threshold would plausibly bind when the index rises late rather than early: wheat and clover sown together, an autumn-sown wheat already shading the clover in March, or a service crop that grows tall before it closes its canopy, such as sole lucerne. I have not run those cases.

So in these settings the date follows a value that is set in the source file. The last section is the change that makes it settable.

4 · The change

Give the other three gates the route the threshold already has

The finding is about a configuration path, so the remedy is a configuration path. Your code already calls the height and the critical index a "configurable default", and MOWING_REFERENCES.md answers "Configurable? Yes" for the height; the first patch makes that true for the trial file and the API.

def apply_mow_decision(
    physics: dict,
    mow_threshold: float = 0.30,
    *,
    min_height_cm: float = MIN_MOW_HEIGHT_CM,
    min_interval_days: int = MIN_MOW_INTERVAL_DAYS,
    critical_comp_index: float = CRITICAL_COMP_INDEX,
) -> dict:

Patch 1 adds the three keyword arguments above, each defaulting to today's constant, so every existing caller gets the same result. The trial file and POST /api/crop/trial-config accept minMowHeightCm, minMowIntervalDays and criticalCompIndex beside mowThreshold, and the local, REST and C# provider wrappers pass them through. They join the trial hash only when a trial sets them, so existing trial hashes do not change. One test is added. The dashboard is left alone.

Patch 2 fixes the window log in the same file. It compared the last logged date with yesterday while only first days are logged, so a continuous run of recommended days was logged as a new window every second day; the closed-loop cut dates on this page are identical with and without it.

With all four gates settable, the rule can be swept as a whole, which is where a question about trade-offs between the gates would start.

How it was built

Method, self-check and sources

The study imports run_treatment_physics and apply_mow_decision from the archived MIT-licensed crop_model/ and changes nothing in them; the height sweep sets the module constant before each run. Weather comes from fetch_daily_weather at the coordinates in your trial file, completed years only, so every simulated day carries real weather. One season takes about a fifth of a second, and the grid of 630 seasons about two minutes. The three scripts and the order to run them are in study/; they need Python 3 and your crop_model/ folder and nothing else.
